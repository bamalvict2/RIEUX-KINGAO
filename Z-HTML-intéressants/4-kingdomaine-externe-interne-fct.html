Architecture KINGDOMAINE – Interne, Externe et Monitoring

1. Deux mondes bien séparés

Ton architecture KINGDOMAINE est organisée en deux univers clairement séparés :

Monde interne – API C# locale

InterneHTTPKestrelDocker
  • API .NET qui tourne en HTTP local (ex : http://localhost:5010).
  • Mode Development : certaines routes (comme /health) ne sont pas exposées.
  • Utilisée pour le développement, les tests, la logique métier, les pages Razor internes.
  • Non exposée au public, non accessible via Internet.

Monde externe – API publique via Cloudflare

ExterneHTTPSCloudflareProduction
  • API accessible via ton domaine (ex : https://solaize.duckdns.org).
  • Mode Production : la route /health est exposée et renvoie 200 OK.
  • Protégée par Cloudflare (tunnel, proxy, SSL, DNS).
  • C’est ce que voient les utilisateurs réels et les clients externes.

2. Une vraie étanchéité entre interne et externe

Il existe une étanchéité logique entre :

  • l’API locale en HTTP (interne),
  • et l’API publique en HTTPS via Cloudflare (externe).

Concrètement :

  • Les routes, les ports et les modes (Dev/Prod) ne sont pas les mêmes.
  • Le monde interne peut évoluer sans casser l’externe.
  • Le monde externe peut être monitoré et mis à jour sans toucher à l’interne.
  • Cette séparation est souhaitable : plus de sécurité, moins de complexité.

3. Rôle de Kestrel dans cette séparation

Kestrel est le serveur web interne de .NET. Il permet :

  • de faire tourner l’API en HTTP local pour le développement,
  • tout en ayant une version Production exposée en HTTPS via Cloudflare,
  • sans mélanger les deux environnements.

Grâce à Kestrel, tu peux :

  • modifier ton API locale, redémarrer Docker, tester des routes internes,
  • sans impacter l’API publique utilisée par les clients.

4. Monitoring externe avec Prometheus et Grafana

PrometheusGrafanaBlackbox Exporter

Le monitoring se concentre sur le monde externe :

  • Blackbox Exporter teste ton API comme un vrai client externe :
    • DNS, Cloudflare, HTTPS, certificat SSL, route /health, temps de réponse.
  • Prometheus collecte ces métriques.
  • Grafana affiche :
    • disponibilité (uptime),
    • latence (p50, p90, p99),
    • codes HTTP (2xx, 4xx, 5xx),
    • état du tunnel Cloudflare, DNS, SSL, etc.

Important : ce monitoring externe ne dépend pas de l’API locale en HTTP. Tu peux donc surveiller l’externe sans jamais toucher à ton code C# interne.

5. Ce que tu peux faire en parallèle

Côté externe – avec Grafana

  • Créer des dashboards pour :
    • disponibilité HTTPS,
    • latence,
    • erreurs HTTP,
    • Cloudflare, DNS, SSL, etc.
  • Construire un vrai cockpit externe pour KINGDOMAINE.

Côté interne – avec ton API C#

  • Créer des pages Razor internes (outils, admin, debug).
  • Ajouter des endpoints internes non exposés au public.
  • Faire évoluer ta logique métier librement.

Les deux mondes peuvent évoluer, dialoguer et être mis à jour sans se gêner mutuellement.

6. Résumé en une phrase

Ton API locale en C# (HTTP) et ton monitoring externe (Prometheus + Grafana + Cloudflare + Blackbox) sont étanches, complémentaires et peuvent évoluer en parallèle sans conflit : interne pour le métier, externe pour la disponibilité réelle.
