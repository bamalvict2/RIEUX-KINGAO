TDD – Solaize SDK (API, Cockpit, Monitoring, Docker)

Vue technique cockpitifiée – API .NET, Blazor Server, MongoDB, Grafana, Prometheus, Nginx, Docker Compose.

A. Vue globale – Architecture technique complète

1. Composants principaux

  • API SolaizeApi – .NET 8, REST, MongoDB, Swagger.
  • Cockpit SolaizeCockpit – Blazor Server, UI opérateur.
  • Infra MongoDB – stockage Items.
  • Monitoring Prometheus – collecte métriques.
  • Monitoring Grafana – dashboards.
  • Infra Nginx – reverse proxy / frontal HTTP.
  • Docker docker-compose.yml – orchestration.

2. Flux principaux

Blazor (Cockpit) ──→ API (SolaizeApi) ──→ MongoDB │ │ │ └──→ /metrics (Prometheus) ──→ Grafana │ └──→ via Nginx (optionnel, frontal unique)

3. Ports et endpoints

  • API : interne http://solaize-api:8080, exposé 8080:8080, Swagger /swagger.
  • Cockpit : interne http://solaize-blazor-server:80, exposé 5000:80.
  • MongoDB : 27017:27017.
  • Prometheus : 9090:9090.
  • Grafana : 3000:3000.
  • Nginx : 80:80 (si utilisé comme frontal unique).

4. Fichiers critiques

  • API : SolaizeApi/Program.cs, Controllers/, Services/, MongoSettings.cs, appsettings.json, Dockerfile.
  • Cockpit : SolaizeCockpit/Program.cs, Pages/, Dockerfile.
  • Monitoring : prometheus.yml (scrape API), dashboards Grafana.
  • Infra : docker-compose.yml, config Nginx.
Point bloquant global : si l’un des services (API, Mongo, Prometheus, Grafana, Cockpit) n’est pas sur le réseau solaize-net ou n’a pas le bon port, la chaîne se casse.

B. Modules – API, Cockpit, Monitoring, Docker

1. Module API (.NET 8 – SolaizeApi)

1.1. Program.cs – pipeline minimal complet

var builder = WebApplication.CreateBuilder(args);

// MongoSettings
builder.Services.Configure<MongoSettings>(
    builder.Configuration.GetSection("Mongo")
);

// MongoClient
builder.Services.AddSingleton<IMongoClient>(sp =>
{
    var settings = sp.GetRequiredService<IOptions<MongoSettings>>().Value;
    return new MongoClient(settings.ConnectionString);
});

// Services
builder.Services.AddScoped<ItemService>();
builder.Services.AddScoped<UploadService>();

builder.Services.AddControllers();
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

builder.Services.AddCors(o =>
    o.AddPolicy("AllowAll", p => p.AllowAnyOrigin().AllowAnyMethod().AllowAnyHeader())
);

var app = builder.Build();

app.UseSwagger();
app.UseSwaggerUI();

app.UseCors("AllowAll");

app.MapControllers();

app.Run();
Point bloquant API : l’oubli de app.UseSwagger(), app.MapControllers() ou app.Run() rend l’API silencieuse (démarre puis s’arrête, exit 0, aucun log).

1.2. appsettings.json – Mongo

{
  "Mongo": {
    "ConnectionString": "mongodb://solaize-mongo:27017",
    "Database": "SolaizeDb",
    "Collection": "Items"
  },
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  }
}
Point de vigilance : les noms de sections doivent correspondre exactement à MongoSettings et à builder.Configuration.GetSection("Mongo").

1.3. Dockerfile API

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

COPY *.csproj ./
RUN dotnet restore

COPY . ./
RUN dotnet publish -c Release -o /app/publish

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .
ENV ASPNETCORE_URLS=http://+:8080
EXPOSE 8080
ENTRYPOINT ["dotnet", "SolaizeApi.dll"]
Point bloquant build API : le context Docker doit être ./SolaizeApi. Sinon, Docker compile un projet vide.

3. Module Monitoring (Prometheus + Grafana)

3.1. Prometheus – scrape API

scrape_configs:
  - job_name: "solaize-api"
    static_configs:
      - targets: ["solaize-api:8080"]
Point bloquant Prometheus : si l’API n’expose pas /metrics ou si la cible est mauvaise, aucun dashboard Grafana ne sera alimenté.

3.2. Grafana – datasource

Datasource Prometheus pointant vers http://prometheus:9090.

4. Module Docker / Compose

4.1. docker-compose.yml – extrait clé

services:
  solaize-api:
    build:
      context: ./SolaizeApi
      dockerfile: Dockerfile
    container_name: solaize-api
    ports:
      - "8080:8080"
    networks:
      - solaize-net
    restart: always
    environment:
      - ASPNETCORE_URLS=http://0.0.0.0:8080
      - ConnectionStrings__Mongo=mongodb://solaize-mongo:27017
      - Mongo__Database=SolaizeDb
      - Mongo__Collection=Items

  solaize-blazor-server:
    build:
      context: ./SolaizeCockpit
      dockerfile: Dockerfile
    container_name: solaize-blazor-server
    ports:
      - "5000:80"
    networks:
      - solaize-net
    restart: always
    depends_on:
      - solaize-api
Point bloquant Docker : un mauvais context ou un mauvais dockerfile produit des images incohérentes (API vide, comportement silencieux).

D. Version manager-friendly – Résumé architecture

1. Objectif

Le système Solaize fournit un cockpit opérationnel (Blazor) connecté à une API .NET, avec stockage MongoDB et supervision par Prometheus/Grafana, le tout orchestré par Docker Compose.

2. Vue simple

  • Cockpit : interface utilisateur pour consulter et manipuler les Items.
  • API : cœur métier, expose des endpoints REST, parle à MongoDB.
  • MongoDB : base de données des Items.
  • Prometheus : collecte des métriques techniques.
  • Grafana : tableaux de bord de supervision.
  • Docker Compose : lance tous les services ensemble, de manière reproductible.

3. Points de contrôle clés

  • Swagger disponible sur l’API → prouve que l’API tourne et que les endpoints sont exposés.
  • Cockpit accessible → prouve que Blazor est déployé et que la chaîne front fonctionne.
  • MongoDB accessible → prouve que les données sont persistées.
  • Prometheus + Grafana opérationnels → prouve que la supervision est en place.
  • docker-compose up --build → un seul point d’entrée pour lancer tout le système.

4. Risques majeurs (en langage simple)

  • API silencieuse : si la configuration de démarrage est incomplète, l’API démarre puis s’arrête sans erreur visible.
  • Mauvais câblage : si les services ne sont pas sur le même réseau ou n’ont pas les bons ports, ils ne se voient pas.
  • Monitoring absent : sans Prometheus/Grafana, on ne voit pas les problèmes avant qu’ils ne deviennent critiques.

Ce TDD sert de carte de navigation : il montre les composants, leurs liens, les fichiers critiques et les points de rupture possibles. Il doit être mis à jour à chaque évolution majeure.
